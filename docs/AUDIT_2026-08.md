# ELANORA repository and architecture audit

**Assessment baseline:** repository revision `0f38154abd1827764161e3b767e5d6a9347e97e9`  
**Engineering target date:** 31 August 2026  
**Audit performed:** 3 September 2026

## Executive assessment

ELANORA has the useful core of a research collaboration prototype. It already models institutional instances, projects, users, invitations, project membership, naming standards, tier views, upload review, notifications, and Git-backed EAF histories. The frontend is substantial and the production bundle builds. The project therefore should not be discarded.

It is not safe to deploy for real research data in its current form. The central promise—preserve all research information and enforce a protocol—is not yet upheld. The raw EAF files are retained in local Git repositories, but upload validation was only an extension/MIME/size check, the searchable database representation drops much of EAF 3.0, and the Git/database/filesystem operations cannot be made atomic. Access control is inconsistent, the database cannot be recreated from a versioned migration history, and one shared mutable Git worktree is unsafe under concurrent web requests.

The recommended direction is a modular monolith with PostgreSQL as the transactional control plane, immutable content-addressed EAF/media objects as the preservation plane, an explicit revision/review model as the collaboration plane, and Git as an import/export or derived-history interface rather than the primary concurrency mechanism. This is simpler to operate and much easier to prove correct.

## Remediation status — 3 September 2026

The implementation pass following this baseline audit completed the immediate
code-level recovery work. ELANORA now validates uploads against a vendored EAF
3.0 XSD and deterministic semantic/reference rules, parses into typed lossless
domain records, and retains exact source bytes and checksums in immutable EAF
revisions. PostgreSQL is the deployment database, SQLAlchemy uses a lifespan
managed pool, and an Alembic migration recreates all current model metadata.
Users and projects are explicitly institution-scoped, project routes use
central authorization guards, project paths reject traversal, and mutating Git
operations are serialized across processes.

The quality baseline is also repaired: backend lint and the strict typed
architectural boundary pass. Forty backend tests cover real EAF documents,
persistence, authorization, retention, bootstrap, and authentication; the nine
database integration scenarios now run against disposable PostgreSQL 18 after
the complete Alembic migration chain rather than creating an SQLite schema
directly. Fourteen frontend tests pass, both applications build, and
backend/frontend advisory audits report no known dependency vulnerabilities.
CI repeats formatting, linting, typing, tests, builds, audits, and migration
drift checks; Dependabot supplies scheduled update proposals.

This does not make the platform operationally complete. Normal deletion now
tombstones relational state and retains immutable EAF revisions; the same-host
Git copy is also preserved, but it is still only a recovery cache. Before
identifiable research data is admitted, an institution must add
versioned encrypted off-host database/object backups, restore drills, retention
and deletion governance, monitoring, secret management, and a privacy/security
review. Git is now serialized for correctness but remains a scalability bridge;
isolated worktrees or revision-native change sets remain the long-term target.

## What exists today

The codebase is a Vue 3/Vite client and a Python 3.13/FastAPI/SQLAlchemy async backend. MySQL 8.4 is the configured database. Each ELANORA project is also a filesystem directory with its own non-bare Git repository and an `elan_files` folder. Uploads are committed to temporary branches, recorded as pending uploads, and later inspected or merged by an administrator. A second local folder copies each project's `.git` directory and current EAF files as a backup.

The current product surface includes:

- invitation-based registration, password reset, cookie JWT sessions, CSRF middleware, and two global roles;
- institutional instance metadata and project membership with read/write/admin-like project permission values;
- project creation, upload, branch inspection, merge/conflict screens, rename, synchronization, restore, and deletion;
- configurable file types, filename standards, standard components, accepted values, and locations at which a standard is effective;
- EAF parsing into files, media descriptors, tiers, annotations, and shared annotation values;
- English, French, and Japanese frontend localization;
- Docker configurations for development, production, and server deployment.

This is meaningful prototype work. The main problem is that several screens and tables imply guarantees that the backend does not yet enforce.

## Critical findings

### 1. EAF handling is not lossless or protocol-complete

The twelve included examples are EAF 3.0 files. Collectively they use `LINGUISTIC_TYPE`, `CONTROLLED_VOCABULARY`, `CV_ENTRY_ML`, `LANGUAGE`, `LOCALE`, `EXTERNAL_REF`, `PROPERTY`, `LINKED_FILE_DESCRIPTOR`, `REF_ANNOTATION`, and many relationship attributes. The parser only projects basic file metadata, three media fields, tier name/parent name, annotation value, and alignable start/end times.

Consequences include:

- reference annotations are stored with start and end time `0` instead of retaining `ANNOTATION_REF` and resolving the reference graph;
- linguistic types, stereotypes, controlled vocabulary references and entry IDs, annotators, participants, languages, locales, licenses, properties, external references, and linked files are not represented;
- empty annotation values are skipped even when preserving the authored document matters;
- a time slot without `TIME_VALUE` is converted through `int(None)` and can fail, rather than being represented as unaligned;
- no bundled XSD is selected from the declared EAF version;
- no ELAN semantic checks are implemented for constraints that XSD cannot express, such as tier overlap rules.

The official EAF 3.0 description explicitly says schema validation is insufficient by itself and documents extra validity/editability rules. ELAN's own validator performs XML validation plus common additional checks. The repository must match that two-level approach: [EAF 3.0 format description](https://www.mpi.nl/tools/elan/EAF_Annotation_Format_3.0_and_ELAN.pdf) and [ELAN validation documentation](https://www.mpi.nl/corpus/html/elan/ch01s02s11.html).

**Decision:** always preserve the exact uploaded bytes as an immutable revision. Treat the relational representation as a rebuildable projection, never as a replacement for the EAF.

### 2. Access control has server-side gaps

Several API modules expose project configuration without an authenticated dependency. The tier module includes create, rename, delete, and move operations without a guard. Project naming standards, project file types, and project-location/file-type mappings likewise contain unguarded mutations. The Git commit and branch-list endpoints are unguarded. Other file operations require any authenticated user but do not consistently verify membership and permission for the named project.

Frontend navigation guards are not a security boundary. This is a classic object-level authorization problem: possession of a project ID or name can be enough to read or mutate another project.

**Decision:** centralize authorization around `(institution_id, project_id, actor_id, capability)`. Every service method—not just every route—must require an authorization context. Use default deny. Retain global instance administration separately from project owner/maintainer/contributor/reviewer/viewer roles.

### 3. The database schema is not reproducible

There is no Alembic configuration or migration directory. `website/database/README.md` is empty. Docker mounts that folder as `/docker-entrypoint-initdb.d`, but the actual `dump.sql` is ignored and machine-local. The tracked `PROJECT-ELANORA_V12.ddl` is an old design and omits many tables used by the ORM. A fresh clone therefore has no trustworthy path to the schema expected by the application.

The local dump is also a full server export containing MySQL system databases and several megabytes of help content. It must not become the migration strategy or be committed.

**Decision:** models plus reviewed migrations are the schema source of truth. Seed only non-sensitive reference data in explicit seed migrations or commands. Test upgrade from empty and from the previous release in CI.

### 4. One mutable Git worktree cannot safely serve concurrent requests

The application switches a project's shared checkout among `master`, upload branches, conflict branches, and merge states. There is no per-project process lock or distributed lock. Two workers or requests can change `HEAD`, index, or working files beneath one another. A merge-readiness GET even performs a real merge and abort in the shared worktree, so a read operation mutates repository state.

The application also performs filesystem writes, Git commits, and database commits in separate steps. A database rollback cannot undo a Git commit or folder creation; a Git failure cannot roll back already committed database changes. Current backup calls occur during low-level Git operations, sometimes before the intended operation is complete.

**Decision:** move collaboration to immutable revisions and change sets. If Git compatibility is retained, operate on a bare repository through serialized background jobs and isolated temporary worktrees. Never switch a shared production checkout from an HTTP request.

### 5. “Backup” is a same-disk working copy, not disaster recovery

The backup folder is on the same host beside the project folder, is overwritten in place, and is deleted when the project is deleted. It has no independent retention, encryption policy, checksums, database coordination, off-site copy, or automatic restore verification. It does not protect against disk loss, ransomware, operator deletion, or a logically corrupted revision.

**Decision:** define RPO/RTO, use versioned encrypted off-host backups for PostgreSQL and object storage, keep an append-only audit/revision ledger, and run scheduled restore drills. Deletion should be a tombstone plus retention workflow, not immediate destruction of both primary and backup.

### 6. Deployed authentication behavior is inconsistent

Production/server environment files use `SECRET_KEY`, while the application reads `JWT_SECRET_KEY`. The ignored local files therefore do not describe a working repeatable deployment. Cookies are marked secure only when `ENVIRONMENT == "prod"`; the externally hosted `server` mode receives non-secure cookies. The CSRF middleware excludes the entire `/api/v1/auth/` prefix, not only the few unauthenticated bootstrap actions. Refresh tokens have no server-side session record, rotation-family detection, or revocation after theft.

Error handling frequently returns raw exception messages to clients, potentially disclosing paths, Git output, SQL details, or internal state. Prior to this audit, logs also included database URLs and CSRF token values.

**Decision:** replace scattered environment reads with validated settings that fail closed at startup. Model server-side sessions, hash stored refresh tokens, rotate them, revoke families on reuse, and use institution SSO/OIDC where available. Keep generic client errors and correlated structured server logs.

### 7. Current quality gates do not protect releases

Audit results before the narrow fixes in this report:

- backend tests: **2 failed of 2** because the tests call a FastAPI `Depends` object as if it were the session generator;
- backend Ruff: **423 errors**;
- backend mypy: **394 errors in 62 files**;
- frontend ESLint: **7 errors and 92 warnings**;
- frontend Vitest: **no test files**, exit status 1;
- frontend production build: succeeds, but emits a roughly 1 MB JavaScript chunk and a code-splitting warning;
- CI configuration: absent.

The repository-level Git hook is optional local tooling and currently calls pre-commit without passing staged filenames correctly. It cannot replace protected-branch CI.

**Decision:** establish one repeatable `make check` or equivalent and require it in CI. First baseline existing debt without hiding it, then ratchet allowed violations downward. Add tests around invariants, not only route snapshots.

### 8. Known dependency vulnerabilities require a controlled upgrade

A live `pip-audit` of the installed backend environment reported **57 advisory matches in 16 packages**. Production-relevant findings include old `starlette`, `python-multipart`, `cryptography`, `lxml`, `aiosmtplib`, and `asyncmy`; some require upgrading FastAPI or replacing a dependency rather than a patch-level lock refresh. The existing `python-jose` stack also brings the pure-Python `ecdsa` package, for which one reported issue has no fixed version.

The initial live npm production audit reported seven vulnerable packages, including direct Axios and Unhead dependencies. The corrections accompanying this audit update those packages and override vulnerable transitive PostCSS/Nanoid versions; the production-only npm audit is now **0 known vulnerabilities**. The complete development dependency tree still reports **22 vulnerabilities**, including Vite/Vitest-related advisories, and needs a deliberate major-version toolchain upgrade.

**Decision:** add automated dependency review, SBOM generation, pinned container digests, and scheduled upgrades. Do not run `npm audit fix` automatically in a startup script; dependency changes belong in reviewed commits with tests.

## Important data-model defects

The present relational schema is an extraction cache, but it is treated as authoritative in several workflows. These defects can produce wrong answers even without an attacker:

- tiers are globally looked up by `tier_name`; the same name in two documents can share one row and one parent relationship despite different linguistic definitions;
- file lookup/update paths sometimes search globally by filename before checking project association, so equal filenames across projects are unsafe;
- a file update deletes and recreates records instead of appending a revision and retaining provenance;
- `last_modified` comes from server filesystem metadata, not an authored or immutable ingest event;
- annotations lack revision identity, reference-annotation linkage, previous-annotation linkage, CV entry identity, and provenance;
- institution scope is frequently hard-coded as `instance_id = 1`;
- standards are mutable rows, so past validation cannot reliably state which exact protocol version approved a revision;
- validation reports are not immutable evidence attached to the revision and validator version;
- comments, approvals, and audit events are not consistently bound to immutable revisions/change sets;
- missing database constraints allow invalid time ranges and other states to be stored;
- the async SQLAlchemy engine is created per request instead of being one lifespan-managed pool.

## Recommended target architecture

Keep this a **modular monolith** until evidence shows that separate services are needed. Institutions need a dependable appliance, not a distributed-systems project.

```text
Browser / ELAN desktop
        |
        v
Reverse proxy + OIDC/session boundary
        |
        v
FastAPI modular monolith
  | identity & authorization
  | projects & memberships
  | revisions & change sets
  | protocols & validation
  | comments, review & audit
  | background-job outbox
        |
        +--------------------+
        v                    v
PostgreSQL 18          Immutable object storage
transactional state   original EAF/media/checksums
and query projection  versioning/retention
        |
        v
Worker queue: validate, extract, diff, export, index
        |
        v
Optional bare-Git export / isolated temporary worktree
```

### PostgreSQL recommendation

Use PostgreSQL 18.6 for a new production baseline as of August 2026; PostgreSQL 19 is still beta. PostgreSQL 18 is supported until November 2030, and the project recommends staying on the current minor release: [PostgreSQL versioning policy](https://www.postgresql.org/support/versioning/) and [PostgreSQL 18 documentation](https://www.postgresql.org/docs/18/).

PostgreSQL is a particularly good fit here because:

- row-level security can provide a second default-deny institution/project boundary beneath application checks;
- range types and GiST exclusion constraints can represent and query aligned time intervals and, where a protocol requires it, prevent overlapping intervals on a tier;
- JSONB can retain version-specific EAF attributes in the projection without discarding new fields, while core identities remain normalized;
- transactional DDL, strong constraints, deferred foreign keys, recursive queries, full-text search, and mature backup/replication tooling fit the graph-like EAF model.

PostgreSQL documents both row-level policies and exclusion constraints directly: [row security](https://www.postgresql.org/docs/18/ddl-rowsecurity.html), [range types](https://www.postgresql.org/docs/18/datatype-rangetypes.html), and [constraints](https://www.postgresql.org/docs/18/ddl-constraints.html).

### Preservation and revision model

Use these separations explicitly:

1. **Original object:** exact uploaded bytes, SHA-256/strong checksum, size, media type, uploader, ingest time, object key, and retention state. It is immutable.
2. **Document revision:** stable document identity plus revision ID, parent revision(s), original object, declared EAF version, author metadata, and lifecycle state.
3. **Projection:** complete searchable representation of that revision. It can be rebuilt when the parser changes.
4. **Validation run:** revision ID, protocol-profile version, validator build/version, timestamps, result, and structured issues with stable codes and XML locations.
5. **Change set:** proposed revisions, base revisions, author, discussion, approvals, merge decision, and resulting revisions.
6. **Audit event:** append-only actor/action/target/result/correlation record. Sensitive payloads stay out of logs.

Object versioning and retention are suitable for the preservation plane. Where supported, object-lock modes plus checksums add protection against accidental or malicious deletion; the operational consequences must be designed before enabling an irreversible bucket setting. See the [S3 Object Lock guidance](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-managing.html).

### Suggested schema modules

| Module | Principal tables |
| --- | --- |
| Tenancy | `institution`, `user_account`, `identity`, `institution_membership` |
| Projects | `project`, `project_membership`, `role`, `capability`, `project_policy` |
| Preservation | `asset`, `asset_version`, `checksum`, `retention_hold` |
| EAF revisions | `document`, `document_revision`, `media_descriptor`, `linked_file`, `property` |
| EAF projection | `tier`, `linguistic_type`, `time_slot`, `annotation`, `annotation_value`, `language`, `controlled_vocabulary`, `cv_entry`, `external_reference` |
| Protocols | `protocol`, `protocol_version`, `rule`, `naming_rule`, `vocabulary_binding` |
| Validation | `validation_run`, `validation_issue`, `validator_release` |
| Collaboration | `change_set`, `change_item`, `review`, `comment`, `merge_result` |
| Operations | `audit_event`, `outbox_event`, `job`, `idempotency_key` |

Every EAF projection row must be scoped to a `document_revision_id`; tier and annotation IDs are only unique within their correct EAF scope. Protocol versions become immutable after publication. Use UTC `timestamptz`, explicit `NOT NULL`, foreign keys, unique constraints, check constraints such as `end_ms >= start_ms`, and indexes derived from measured queries. Avoid premature partitioning.

### Validation pipeline

An upload should be quarantined and advance only when these deterministic stages finish:

1. request/body limits, safe flat filename, supported content declaration, malware policy where required;
2. SHA-256 during streaming and immutable write of the exact original;
3. strict XML parsing with DTD/entities/network disabled;
4. XSD validation using a bundled, allow-listed schema selected from the declared EAF version—never a schema fetched from the uploaded URL;
5. EAF semantic validation: all IDs/references, tier/linguistic-type relationships, time-slot semantics, reference chains, stereotypes, ordering and overlap rules, CV/language/external-reference consistency;
6. immutable institution/project protocol validation: filename, required tiers, tier hierarchy, linguistic types, controlled vocabularies, participant/annotator conventions, media linkage, and project-specific rules;
7. extraction into a new revision projection in one database transaction;
8. review/approval based on structured errors and warnings, followed by atomic publication of the new current-revision pointer.

Never rewrite the original to “fix” it. A correction is a new revision whose provenance points to its parent.

For future interchange, retain EAF as the primary compatibility format and consider a lossless Web Annotation JSON-LD export, not a replacement. ELAN itself supports a subset and the W3C model is intended for cross-platform sharing: [W3C Web Annotation Data Model](https://www.w3.org/TR/annotation-model/).

## Privacy, ethics, and accessibility

Sign-language corpora commonly contain identifiable faces, voices, names, affiliation data, and research annotations. Video is personal data when people are identifiable; it becomes biometric special-category data when specific technical processing is used to uniquely identify people. The system therefore needs data classification, purpose/legal-basis records, consent or research-basis handling, participant withdrawal workflows, least privilege, encryption, pseudonymization support, access audit, retention schedules, and a documented breach/incident process. A DPIA should be evaluated per institution and dataset.

GDPR Article 5 requires data minimization, storage limitation, integrity/confidentiality, and protection against accidental loss; scientific-research retention still requires Article 89 safeguards. See the [official GDPR text](https://eur-lex.europa.eu/legal-content/EN/TXT/PDF/?uri=CELEX%3A02016R0679-20160504) and the EDPB's [2026 scientific-research guidance](https://www.edpb.europa.eu/system/files/2026-04/edpb_guidelines_202601_scientificresearch_en.pdf). This is engineering guidance, not a substitute for institutional legal/ethics review.

Because the users include sign-language researchers and potentially Deaf researchers, target WCAG 2.2 AA, keyboard-only workflows, visible focus, accessible status messages/conflict views, non-drag alternatives, captions/transcripts for instructional media, and sign-language onboarding where the community requests it. WCAG 2.2 is now also ISO/IEC 40500:2025: [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/).

## Recovery plan

### Phase 0 — Freeze risk and create a trustworthy baseline (1–2 weeks)

- Do not deploy real or identifiable research data yet.
- Rotate any secret that has ever appeared in a local environment file or log.
- Record supported EAF versions and collect a sanitized golden corpus: valid, invalid, edge-case, legacy, controlled-vocabulary, reference-annotation, and unaligned examples.
- Add CI for backend tests/lint/type checks, frontend tests/lint/build, dependency audit, secret scanning, container scan, and migration smoke tests.
- Upgrade vulnerable backend runtime dependencies in a dedicated branch; replace `python-jose` if its dependency chain cannot be secured.
- Add server-side guards to every endpoint and service, then write negative authorization tests first.
- Document current deployments and take verified exports before any database migration.

**Exit gate:** no anonymous mutation; no known high/critical runtime advisory without an accepted, time-bounded exception; repeatable checks run in CI; current data can be restored in a disposable environment.

### Phase 1 — Establish the data and tenancy foundations (2–4 weeks)

- Write ADRs for PostgreSQL, immutable object storage, revision identity, tenancy boundary, Git compatibility, and deployment topology.
- Introduce PostgreSQL 18 and Alembic with an empty-to-head migration test.
- Implement institution/project capability authorization and optional PostgreSQL RLS.
- Add lifespan-managed database pooling, readiness checks, structured configuration validation, and idempotency keys.
- Build one-way import tooling from the current MySQL schema and reconcile counts/checksums.

**Exit gate:** a fresh clone creates the same schema; cross-project and cross-institution access tests fail closed; migration reconciliation is exact.

### Phase 2 — Build lossless EAF ingestion (3–5 weeks)

- Bundle versioned official EAF schemas with recorded provenance and checksums.
- Implement strict XSD plus semantic validation with stable issue codes.
- Redesign the projection around immutable document revisions and full EAF identity/reference semantics.
- Add versioned protocol profiles and deterministic validation reports.
- Property-test parser invariants and round-trip/export behavior against the golden corpus.

**Exit gate:** every accepted original is byte-retrievable by checksum; projections rebuild deterministically; all represented sample features survive export or are explicitly retained as extension data; invalid documents cannot become current.

### Phase 3 — Replace shared-worktree collaboration (4–8 weeks)

- Implement change sets, optimistic concurrency on base revision, reviewer approval, comments, and append-only audit.
- Implement EAF-aware semantic diff at document/tier/annotation/metadata level.
- Define merge rules per field; require humans for ambiguous time, hierarchy, CV, and delete/modify conflicts.
- Provide Git import/export through background jobs and isolated worktrees if researchers need Git interoperability.

**Exit gate:** concurrent submissions cannot alter each other's state; conflicts are deterministic and attributable; publication is one atomic pointer change.

### Phase 4 — Production operations, privacy, and accessibility (3–5 weeks)

- Harden containers: supported LTS runtimes, non-root users, read-only filesystems where possible, pinned image digests, minimal capabilities, health checks, and resource limits.
- Add metrics/traces/log correlation without research content or credentials, plus alerting and runbooks.
- Implement encrypted off-host backup, point-in-time database recovery, object-version retention, and scheduled restore drills.
- Complete threat modeling, DPIA support, retention/deletion/legal-hold design, and audit export.
- Test WCAG 2.2 AA with automated tools and Deaf/disabled users.

**Exit gate:** agreed RPO/RTO demonstrated by a restore drill; security/privacy review signed off; accessibility acceptance completed.

### Phase 5 — Controlled pilot

- Pilot one institution, one small non-sensitive/sanitized corpus, and a limited researcher group.
- Measure upload/validation latency, protocol false positives, review effort, conflict frequency, restore time, and usability.
- Only then admit identifiable video and expand institutions.

## Corrections included with this audit

- upload validation is now asynchronous and invokes strict XML content validation before the service writes a branch;
- XML recovery is disabled, DTD declarations are rejected, entity/network loading remains disabled, and real byte size is checked;
- configured file and batch limits replace duplicated hard-coded limits;
- flat upload filenames reject path separators, traversal names, and NUL bytes;
- Git stages uploaded files after `--`, preventing option-like names from being interpreted by Git;
- database URLs and CSRF token values are no longer logged;
- six upload-boundary tests cover valid EAF, pointer reset, malformed XML, traversal names, and DTD rejection;
- Axios, Unhead, PostCSS, and Nanoid were updated/overridden to patched versions; `npm audit --omit=dev` reports zero known vulnerabilities.
- generated build and coverage directories are excluded from ESLint, and seven dead-code lint errors were removed; lint now exits successfully with 92 style warnings.

These corrections reduce immediate exposure. They do not constitute EAF schema/semantic conformance, complete authorization, a safe database migration, or production readiness.
